# Rendering a Morning Coffee snapshot

Collect and normalize source facts once, then render through the bundled helper:

```sh
python3 scripts/render_brief.py /tmp/snapshot.json /tmp/morning-coffee.html
```

The helper uses only Python's standard library. It reads sibling `assets/brief.css` and `assets/brief.js`, then inlines both into the output. It does not call providers, update memory, or open a browser. The resulting report makes no network calls during rendering. Links remain ordinary user-initiated navigation. Keep raw collection data and previews temporary; publish new reports through [daily-history.md](daily-history.md). Never commit real report data with the helper.

The daily history helper consumes anonymous `availability` from [focus-and-exercise.md](focus-and-exercise.md), derives `day_plan`, and adds history/change metadata. Coffee is the complete daily overview, with up to four priorities, interactive calendar/local plan submission and all core domains visible. Tea is a smaller intraday snapshot: three unfinished priorities, a short change TL;DR, six visible context cards and a read-only calendar with saved choices. Supporting evidence is expandable; Tea’s full queues may also be collapsed. The full change audit stays in the snapshot. Both retain every eligible fact.

The root JSON object has `schema_version: 1` and these fields. Strings are plain source text, never HTML:

- `report`: `title`, `page_title`, `eyebrow`, local `date`, `time`, IANA `timezone`, optional `preview_label`, and `footer`.
- `coverage`: one compact string for the coverage banner, or an empty string when no notice is needed.
- `priorities`: array of `{title, context, action, done, evidence}` with stable `id` and optional verified `status` (`open`, `in_progress`, `blocked`, `completed`, `resolved`, `cancelled`). Completed/resolved/cancelled items are excluded from the default remaining-work list. `done` is the completion criterion, not a boolean. Evidence is `{paragraphs: [string], links: [{label, url}]}`.
- `okr`: optional `{label, url, period}` with the verified current-quarter link.
- `agenda`: `{coverage, events}`. Every event has `{id, start, end, time, title, url, join_url, join_label}`; `start`/`end` are authoritative offset-aware timestamps (or exclusive-end all-day dates), needed by the interactive calendar. Display-only time strings are never scheduling evidence. Optional `all_day` identifies all-day events; optional `free` and `tentative` booleans add explicit labels. Retain all in-scope events.
- `oncall`: `{schedule, state, responder, shift_label, shift, dashboard_url, counts, note}`. Counts is `{active: integer, triage: integer}` from verified incident data. Omit unsupported counts rather than guessing.
- `rfcs`: `{window_label, database_url, coverage_label, coverage, items}`. An item has `{id, title, url, author, submitted_local, request_emoji, request_label, user_approved, approval_status, summary, relationship, next_action, approval_url}`. Only the collector decides inclusion in the exact In-Review / rolling-14-day window, and only verified user approval sets `user_approved: true`.
- `reviews`: `{collected_label, scopes: [{label, url}], items}`. Items are the complete, deduplicated eligible queue in canonical oldest-first order, after excluding personal approvals without an explicit re-request. Each has `{repository, number, url, title, queue, teams, author, readiness, reviewDecision, mergeStateStatus, ci, effort, updatedAt, summary, changedFiles, commitCount, additions, deletions}`. `authorOnTransport` is true/false for complete roster coverage and null when membership is unknown. `authorRoster` is `{status, note}` with status complete/partial/unavailable, and `personalReview` reports excludedCount, reRequestedCount and unknownCount. Default Authors is Transport team only for a complete roster; otherwise Everyone with a coverage note. `queue` is `direct` or `team`; direct takes precedence over overlaps. `author` is `{login}` or null; `readiness` is `{status, facts}`; `ci` is `{passing, failing, pending, total}` with optional `unknown`; an unavailable total is null; `effort` is `{size, label, inputs, driver}`. Size is S/M/L. Missing or invalid update timestamps render as unavailable. Do not retain full commits, files, raw bodies, or checks in this rendering snapshot. Derive and copy source fields programmatically; author only the concise recommendation/summary text instead of reproducing bulk JSON through the model.
- `yesterday`: `{date, coverage, items: [{title, content}]}` using the same evidence shape as priorities.
- Optional `submitted_plan`: latest same-date/timezone locally saved `{date, timezone, submitted_at, blocks: [{kind, start, minutes}]}` where `start` is local minutes after midnight. The history helper loads it from the configured report root on each run; Tea displays it read-only alongside refreshed events. Keep actual calendar events distinct from submitted choices.
- Optional `status_checks`: records `{section, id, title, outcome, question, attempts}`. Use `outcome: "uncertain"` only after independent validation leaves the item's status unknown; verified records may use `"verified"` and omit `question`. Each attempt is `{source, method, checked_at, result}` with an offset-aware time and the actual attempted authoritative lookup/result; optional `url` identifies its evidence. `section` and `id` match the stable source item or priority. Tea renders questions only for uncertain records with at least one valid recorded attempt, with attempted evidence in details. Plain unknowns without a check are collection work, not questions for the user. Never manufacture checks during format-only previews. Attribute user answers separately, preserving their time and the source-observed state.

The section navigator, readiness/effort distributions, and request totals derive from snapshot rows. They summarize the full retained queue, independent of the Authors default; while the table defaults to ten rows. Filters, adjustable 10/25/50/All pagination, and clear controls operate on the existing DOM; no additional fetching or re-ranking occurs. Every PR is included in the HTML, and all remain visible if JavaScript is unavailable.

# Dense presentation contract

Coffee order: count navigation, all ranked priorities with actions/completion criteria, interactive calendar, quarter-planning link, visible agenda and on-call status, full RFC/review queues, previous-weekday outcomes and source notes. Reviews use the full reading width with existing filters/pagination. Coffee has no closed wrapper around its main domains. Tea order: remaining work, change/new-item TL;DR and necessary questions, six-domain broader-picture snapshot, read-only calendar, expandable complete queues/source evidence. Tea cards show representative rows, total queue sizes, next actions and retained-evidence labels; they are useful even when no source status changed.

Use aligned ledgers for priorities, RFCs, and PRs, with readable typography, moderate row spacing, hairlines, and broad use of available width. The bundled theme is a cutesy Japanese café crossed with retro 8-bit games: ivory panels, cocoa pixel outlines and hard shadows, sakura Coffee accents, matcha Tea accents, CSS pixel cup sprites and decorative kaomoji. Monospace headings add character while body text stays readable. Essential metadata remains comfortably readable; do not shrink it to achieve density. Show data-grounded readiness and size distributions, count navigation, and review-size glyphs. Use muted semantic accents with readable labels and reserve a tinted interruption for coverage. Keep contrast and keyboard focus clear on the pastel reading surfaces. No decorative image assets are needed.

Keep each priority's action and completion checkpoint visible. Keep PR title, author, Direct/Team source, team tags, readiness, CI counts, and numeric size inputs visible. Coffee exposes PR authors and a short neutral summary, RFC proposal summaries/next actions, and Yesterday’s outcomes. Keep full-length PR summaries, effort drivers, precise readiness facts and timestamps in supporting `details` disclosures. Priority/RFC evidence may also use disclosures. Never remove facts to achieve density.

Responsive grids reduce to one column on narrow screens. Wide ledgers span the full reading width; narrow layouts stack fields with no fixed minimum column widths. Explicit table roles preserve row/column semantics when CSS changes table display. Label size shorthand (`f` files, `c` commits), approval checkmarks, and request emojis. Distribution counts must also be readable as text and accessible labels.
